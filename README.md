# ERP (Enterprise Resource Planning)

기업 운영의 핵심 흐름을 단일 서버에서 구현하며 트레이드오프를 검증하는 프로젝트

## 프로젝트 목표

- 비즈니스 시나리오를 먼저 이해하고, 거기에 맞는 기술을 선택한다
- 각 모듈 간 의존성과 데이터 흐름을 직접 설계한다
- 트랜잭션 경계, 동시성, 상태 관리의 트레이드오프를 경험한다
- "왜 이렇게 설계했는가"에 대한 근거를 축적한다

## 기술 스택

- Java 21, Spring Boot 3.x
- PostgreSQL, Redis
- 단일 서버 (MSA 없이 모듈러 모놀리스)

## 모듈 구조
```
/ERP
├── sales/          # 영업/판매
├── procurement/    # 구매/조달
├── inventory/      # 재고/창고 (WMS)
├── production/     # 생산/제조
├── logistics/      # 물류/배송
├── payment/        # 결제/수금
├── settlement/     # 정산/회계
├── hr/             # 인사/급여
├── approval/       # 전자결재
├── auth/           # 권한/접근제어
├── crm/            # 고객관리
├── promotion/      # 포인트/쿠폰
├── notification/   # 알림
├── report/         # 리포트/대시보드
└── docs/           # 설계 문서
```

## 모듈별 핵심 비즈니스 시나리오

### 1. 영업/판매 (Sales)
| 시나리오 | 설명 |
|---------|------|
| 견적 → 수주 | 영업사원이 고객사에 견적서 발송 → 고객 수락 → 수주 등록 |
| 고객별 단가 | 고객사마다 다른 할인율/단가 적용 |
| 납기 약속 | 재고/생산 일정 확인 후 납품 가능일 산출 |
| 수주 잔량 | 수주는 했으나 아직 출고되지 않은 잔량 추적 |
| 견적 만료 | 유효기간 경과 시 자동 만료 처리 |

### 2. 구매/조달 (Procurement)
| 시나리오 | 설명 |
|---------|------|
| 발주 요청 | 재고 부족 알림 → 구매팀 발주 요청서 작성 |
| 견적 비교 | 다수 공급업체 견적 요청 → 비교 후 선정 |
| 발주 확정 | 공급업체에 발주서 전송 |
| 입고 검수 | 납품 시 수량/품질 확인 |
| 반품 처리 | 불량 발견 시 반품, 대체품 요청 |

### 3. 재고/창고 (Inventory/WMS)
| 시나리오 | 설명 |
|---------|------|
| 입고 | 물건 도착 → 바코드 스캔 → 위치 지정 |
| 출고 | 주문 접수 → 피킹 리스트 생성 → FIFO 출고 |
| 재고 실사 | 정기적으로 실제 수량과 시스템 수량 대조 |
| 로트 관리 | 생산일자별 추적 (리콜 대비) |
| 유통기한 | 임박 상품 알림 → 할인/폐기 결정 |
| 창고 이동 | 창고 A → 창고 B 재고 이동 전표 |
| 안전재고 | 기준치 이하 시 자동 발주 요청 트리거 |

### 4. 생산/제조 (Production)
| 시나리오 | 설명 |
|---------|------|
| BOM 관리 | 완제품 1개 = 부품 A x2 + 부품 B x3 |
| 생산 계획 | 주간/월간 생산 목표 수립 |
| MRP | 자재 소요량 계산 → 재고 확인 → 부족분 발주 |
| 작업 지시 | 생산라인에 일일 생산 수량 지시 |
| 생산 실적 | 실제 생산량, 불량 수량 기록 |
| 완제품 입고 | 생산 완료 후 창고 이동 |

### 5. 물류/배송 (Logistics)
| 시나리오 | 설명 |
|---------|------|
| 출고 지시 | 주문 확정 → 창고에 출고 지시 |
| 피킹/패킹 | 상품 수집 → 포장 → 송장 출력 |
| 배차 | 출고 건 묶음 → 배송기사 배정 |
| 권역 라우팅 | 지역별 배송기사 자동 배정 |
| 배송 추적 | 출발 → 배송중 → 완료 상태 변경 |
| 반품 수거 | 고객 반품 요청 → 수거 배차 → 반품 입고 |

### 6. 결제/수금 (Payment)
| 시나리오 | 설명 |
|---------|------|
| 선결제 | 주문 시 즉시 결제 (카드, 계좌이체) |
| 후결제 | B2B 거래, 월말 정산 |
| 부분결제 | 총액 중 일부만 선결제 |
| 부분취소 | 주문 일부 취소 → 해당 금액만 환불 |
| 외상매출금 | 미수금 추적, 연체 관리 |
| 수수료 정산 | 결제수단별 수수료 계산 |

### 7. 정산/회계 (Settlement)
| 시나리오 | 설명 |
|---------|------|
| 전표 생성 | 매출/매입 발생 시 자동 전표 생성 |
| 판매자 정산 | 주기별 매출 집계 → 수수료 차감 → 지급 |
| 세금계산서 | 거래처별 월말 발행 |
| 미수금/미지급금 | 받을 돈 / 줄 돈 관리 |
| 월마감 | 월간 매출/비용/손익 집계 |

### 8. 인사/급여 (HR)
| 시나리오 | 설명 |
|---------|------|
| 직원 관리 | 입사, 퇴사, 부서 이동 |
| 근태 관리 | 출퇴근 기록, 지각/조퇴/결근 |
| 휴가 관리 | 연차 신청 → 잔여일수 차감 |
| 급여 계산 | 기본급 + 수당 - 공제 = 실수령액 |
| 4대보험 | 국민연금, 건강보험, 고용보험, 산재보험 |
| 소급 적용 | 승진/호봉 변경 소급 반영 |
| 연말정산 | 소득공제 항목 반영 |

### 9. 전자결재 (Approval)
| 시나리오 | 설명 |
|---------|------|
| 결재선 설정 | 문서 종류/금액별 결재자 지정 |
| 기안 → 승인 | 문서 작성 → 순차/병렬 결재 |
| 반려 | 사유 작성 후 반려 → 재기안 |
| 대결/위임 | 결재자 부재 시 대리 결재 |
| 후결 | 긴급 건 선처리 후 사후 결재 |

### 10. 권한/접근제어 (Auth)
| 시나리오 | 설명 |
|---------|------|
| 역할 기반 | 영업팀은 영업 메뉴만 접근 |
| 데이터 격리 | 본인 담당 고객사 데이터만 조회 |
| 동적 정책 | 조건부 권한 (금액 한도, 시간대 등) |
| 감사 로그 | 누가 언제 무엇을 했는지 기록 |

### 11. 고객관리 (CRM)
| 시나리오 | 설명 |
|---------|------|
| 고객 등록 | 신규 고객 → 담당 영업사원 배정 |
| 상담 이력 | 문의/요청 내역 기록 |
| 클레임 | 불만 접수 → 처리 → 완료 |
| 고객 등급 | 매출 기준 VIP/일반 분류 |
| 신용 한도 | 외상 거래 한도 설정 |

### 12. 포인트/쿠폰 (Promotion)
| 시나리오 | 설명 |
|---------|------|
| 포인트 적립 | 구매 금액의 N% 적립 |
| 포인트 사용 | 결제 시 포인트 차감 |
| 포인트 소멸 | 유효기간 경과 시 자동 소멸 |
| 쿠폰 발급 | 조건부 할인 쿠폰 발급 |
| 부분취소 환불 | 포인트 사용 주문 취소 시 환불 정책 |

### 13. 알림 (Notification)
| 시나리오 | 설명 |
|---------|------|
| 시스템 알림 | 재고 부족, 결재 요청 등 |
| 이메일/SMS/푸시 | 채널별 발송 |
| 수신 설정 | 사용자별 알림 채널 선택 |
| 발송 이력 | 알림 발송 기록 관리 |

### 14. 리포트 (Report)
| 시나리오 | 설명 |
|---------|------|
| 매출 현황 | 일/주/월별 매출 집계 |
| 재고 현황 | 품목별 재고 수량, 회전율 |
| 부서별 비용 | 부서별 지출 집계 |
| 전년 대비 | YoY 비교 분석 |
| 실시간 대시보드 | 주문/배송 현황 모니터링 |

## 모듈 간 데이터 흐름
```
[Sales] 수주 등록
    ↓
[Inventory] 재고 확인/예약
    ↓ (부족 시)
[Procurement] 발주 요청 → [Production] 생산 지시
    ↓
[Inventory] 입고
    ↓
[Logistics] 출고 → 배송
    ↓
[Payment] 결제/수금
    ↓
[Settlement] 정산/회계
    ↓
[Report] 집계/분석
```

## 구현 우선순위

1. **Phase 1**: inventory → payment → settlement (핵심 금전 흐름)
2. **Phase 2**: sales → procurement (영업/구매 사이클)
3. **Phase 3**: logistics → production (물류/생산)
4. **Phase 4**: hr → approval → auth (내부 운영)
5. **Phase 5**: crm → promotion → notification → report (부가 기능)

## 설계 원칙

- 각 모듈은 독립적으로 동작 가능해야 한다
- 모듈 간 통신은 명확한 인터페이스를 통해서만
- 트랜잭션 경계는 모듈 내부에서 완결
- 모듈 간 데이터 정합성은 이벤트 기반으로 해결
- 모든 설계 결정은 docs/에 근거 기록
